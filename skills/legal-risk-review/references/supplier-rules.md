# 供应商入库审批细则（R1–R9）

> 按需加载。SKILL.md 主干只保留判定流程，本文件是完整规则表。

## 规则表

| 编号 | 规则 | 判定依据 |
| :-- | :-- | :-- |
| R1 | 申请部门为业务部门 → 供应商类型应为「成本类」 | 部门口径见下 |
| R2 | 非业务部门 → 供应商类型应为「费用类」 | 部门口径见下 |
| R3 | 供应商为境外公司，或申请部门为「引力国际」→ 跨境业务应为「是」 | 境外标准未配置，见「尚未确认」 |
| R4 | 企业信息以 OA 自动带出的天眼查信息为当前比对基准 | 基准优先级见 source-contract.md |
| R5 | 营业执照核验：主体名称、统一社会信用代码、注册资本、注册地址、法定代表人 | 附件证据 |
| R6 | 地址省/市/区层级省略可接受；其余 R5 字段不一致即异常 | 仅地址有容错 |
| R7 | 银行核验：户名、开户行、账号、统一社会信用代码 | 附件证据 |
| R8 | 一般纳税人：OA 选择、天眼查信息、上传证明三者一致 | 三方交叉 |
| R9 | 无法从证据确认时，结论必须为「需人工核验」 | 兜底规则，优先级最高 |

## 部门口径

- 业务部门：常规业务部门，如华北、华南。
- 非业务部门：法务、行政、数智中心。
- 拿不准的**必须问本人**，不得自行归类。

## 尚未确认，默认输出「需人工核验」

以下六项刻意留空。遇到时不得猜测、不得用行业惯例补全：

1. 全部业务部门的标准名称 / 部门编码完整名单
2. 「境外公司」的准确判定标准
3. 一般纳税人合格证明的文件类型
4. 银行名称简称是否允许
5. 多个银行账户如何判断
6. 企业名称括号、简称、英文名是否视为一致

## 工具类硬约束（做自动化时必须遵守）

- 不自动提交 OA，不实现任何等效逻辑；只允许「填入审批意见」。
- 不绕过登录、验证码与权限。
- API Key 只放后端环境变量，不进浏览器扩展。
- 模型输出必须过 JSON Schema 校验。
- 附件只在内存处理，不落用户下载目录。
- 单据切换后结果不得串单；连续切换需重新绑定当前单据编号。
